# ЖДЯ-бот для MAX

Чат-бот АО «АК «ЖДЯ» для мессенджера MAX. Отвечает на вопросы, написанные своими словами:
«как купить билет», «хочу сдать билет» → «билет на поезд или талон на трансфер?» → «трансфер».

Весь контент (тексты, варианты ответа, картинки, файлы) хранится в PostgreSQL. Бот перечитывает его каждые
`CONTENT_REFRESH_SECONDS` секунд (по умолчанию 300) как резервную проверку. Для немедленного обновления
есть защищённый `POST /internal/content/refresh`: API уведомляет бот, бот перечитывает контент и возвращает
применённую версию. Перезапуск не нужен. Редактор в админке пока не реализован; при его добавлении после
успешного коммита записи нужно вызвать `notifyBotContentChanged` из `apps/api/src/content-notifier.ts`.
Прямые SQL-изменения сами по себе сигнал не отправляют — после них вызовите этот endpoint (см. `deploy/README.md`).

## Устройство (монорепозиторий pnpm)

```
apps/
  api/       Fastify: единственный, кто работает с БД. /internal/* — для бота (по INTERNAL_API_TOKEN),
             /api/* — для админки (вход по логину и паролю, cookie)
  bot/       MAX: принимает сообщения и отвечает. Данные берет из API, контент держит в кеше
  admin/     React + Vite: дерево разделов (пока только просмотр)
packages/
  core/      контент (дерево, начальный контент seed-data.ts) и диалоговый движок; без БД и сети
  db/        схема Drizzle, миграции (drizzle/), заливка начального контента
  runtime/   общий .env, логгер (logs/<приложение>.log)
tools/
  image-generator/   картинки расписаний и тарифов в media/generated
```

Если API недоступен, бот продолжает отвечать по последнему загруженному контенту, а сессии держит в памяти.
Одновременно работает только один бот: он держит аренду в API, второй экземпляр завершается.

## Быстрый старт (локально)

Нужны Node.js 20.19+, pnpm и Docker.

```bash
pnpm install
cp .env.example .env          # вписать BOT_TOKEN и INTERNAL_API_TOKEN (любая длинная случайная строка)
docker compose up -d          # PostgreSQL на localhost:5433
pnpm admin:create admin       # пользователь админки (пароль спросит в консоли)
pnpm dev                      # API :3001, бот (polling) и админка http://localhost:5173
```

При запуске API сам применяет миграции и, если БД пустая, заливает начальный контент из
`packages/core/src/content/seed-data.ts`. Уже заполненную БД он не трогает: правки из админки сохраняются.
Приложения можно запускать и по отдельности: `pnpm dev:api`, `pnpm dev:bot`, `pnpm dev:admin`.

### Без токена: симулятор чата

```bash
pnpm chat                                    # интерактивно
pnpm chat "как купить билет" "якутск"        # прогнать реплики
pnpm chat --api                              # контент из запущенного API, а не из seed-data.ts
```

- текст — сообщение пользователя;
- `?фраза` — показать косинусное сходство E5 с разделами (без генерации ответа).

## Как бот понимает текст

1. Приветствие («Здравствуйте, …») отрезается; на чистое приветствие бот отвечает стартовым сообщением.
2. «назад» и «меню» обрабатываются как навигация.
3. Единственный поиск по свободному тексту — E5: `intfloat/multilingual-e5-small` в совместимом с Transformers.js
   ONNX-варианте `Xenova/multilingual-e5-small`, закреплённая ревизия, CPU/q8. Модель локально кодирует запрос
   (`query:`) и материалы (`passage:`); mean pooling и нормализация дают косинусное сходство. Это не вероятность.
4. В индекс входят названия, путь раздела и текст ответа; длинные тексты разбиваются на перекрывающиеся фрагменты.
   Для коротких реплик учитывается текущий раздел. Ключевые слова, синонимы, стеммер и лексический fallback удалены.
5. Если два раздела близки по баллу — бот переспрашивает «Уточните, пожалуйста…» и перечисляет варианты;
   ответ на уточнение ищется прежде всего среди них.
6. Если лучший балл ниже порога — подсказка со списком тем и запись в `unrecognized_messages`.
   Команды навигации, номера пунктов, приветствия и «да/нет» остаются детерминированным протоколом,
   а не картой тематических ключевых слов.

### Экспериментальная ветка E5

Первый запуск `pnpm chat` или `pnpm dev` скачивает модель и токенизатор (~135 МБ) в `.cache/e5`.
Нужен интернет для первой загрузки; затем модель работает локально на CPU, без Python и внешнего LLM API.
Поиск не сочиняет ответы: возвращаются исходные тексты/картинки/файлы выбранного раздела.
Содержимое изображений не распознаётся: раздел с расписанием-картинкой ищется по названию и тексту.

`E5_THRESHOLD=0.84` и `E5_AMBIGUITY_GAP=0.025` — начальные экспериментальные пороги, а не гарантия качества.
Они настраиваются в `.env`; `E5_CACHE_DIR` необязателен. После изменения контента строится новый индекс;
синонимы из существующей БД игнорируются. Колонка оставлена ради совместимости без разрушительных миграций.

```bash
pnpm eval:e5             # реальные 22 сценария, включая неоднозначные и посторонние вопросы
pnpm eval:e5 --strict    # ненулевой код выхода, если есть промахи
```

Отчёт в `.cache/e5-evaluation.json` отделяет реальное качество модели от офлайн unit-тестов с моками.
«OK» означает правильный ответ либо уточнение с нужным разделом, не обязательно прямой ответ.
Известные промахи видны в отчёте; маленькая модель не гарантирует понимания любой формулировки.
Во время ошибки модели старый matcher не включается: бот предлагает повторить вопрос или выбрать пункт номером.
Админка пока остаётся только просмотром; это не новый веб-чат. Для проверки в MAX нужен отдельный dev-токен.

## Типы разделов (`content_nodes.type`)

| Тип       | Что делает |
|-----------|------------|
| `section` | Сообщение (текст, картинка, файл). Вложенные пункты перечисляются в сообщении как варианты ответа (уточняющий вопрос); без них — конечный ответ |
| `link`    | Ссылка на внешний сайт (в списке вариантов — кликабельная) |
| `goto`    | Вариант ответа, ведущий в другой раздел (без дублирования текста) |

`is_hidden` — раздел не перечисляется в вариантах, но находится по тексту (так сделан «Возврат билета»).
`is_active` — выключенный раздел и все вложенные в него не перечисляются и не находятся.

## Развертывание на сервере

Docker Compose (PostgreSQL, API, бот в режиме webhook, Caddy с HTTPS) и скрипты выкладки — в [deploy/](deploy/README.md).

## Команды

| Команда | Что делает |
|---------|------------|
| `pnpm dev` | API, бот и админка вместе (`dev:api`, `dev:bot`, `dev:admin` — по отдельности) |
| `pnpm chat` | Симулятор чата |
| `pnpm eval:e5 [--strict]` | Реальный E5-прогон на контрольных вопросах (скачивание модели при первом запуске) |
| `pnpm admin:create <логин> [--role admin|editor]` | Создать пользователя админки или сменить пароль |
| `pnpm test` | Тесты |
| `pnpm typecheck`, `pnpm lint` | Проверки |
| `pnpm db:generate` | Миграция после изменения `packages/db/src/schema.ts` |
| `pnpm db:migrate`, `pnpm db:seed [--force]` | Миграции и начальный контент вручную (`--force` заменяет контент в БД на seed-data.ts) |
| `pnpm generate-images` | Картинки расписаний и тарифов в `media/generated` |

## Сертификаты

API MAX подписан сертификатом НУЦ Минцифры (Russian Trusted Root CA), которого нет в Node.js.
Сертификаты лежат в `apps/bot/certs/` и подключаются только для процесса бота (`apps/bot/src/tls.ts`).
На Node.js < 22.19 запускайте бота с `NODE_EXTRA_CA_CERTS=<абсолютный путь к apps/bot/certs/russian_trusted_root_ca.pem>`.
