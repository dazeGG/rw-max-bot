# ЖДЯ-бот для MAX

Чат-бот АО «АК «ЖДЯ» для мессенджера MAX. Отвечает на вопросы, написанные своими словами:
«как купить билет», «хочу сдать билет» → «билет на поезд или талон на трансфер?» → «трансфер».

Весь контент (тексты, варианты ответа, картинки, файлы) хранится в PostgreSQL. Бот перечитывает его каждые
`CONTENT_REFRESH_SECONDS` секунд (по умолчанию 300) как резервную проверку. Для немедленного обновления
есть защищённый `POST /internal/content/refresh`: API уведомляет бот, бот перечитывает контент и возвращает
применённую версию. Перезапуск не нужен. Редактор дерева в админке после каждой записи вызывает
`POST /api/content/apply`, который и отправляет этот сигнал; если бот не ответил, правка применится при резервной
проверке. Прямые SQL-изменения сигнал не отправляют — после них вызовите endpoint сами (см. `deploy/README.md`).

## Устройство (монорепозиторий pnpm)

```
apps/
  api/       Fastify: единственный, кто работает с БД. /internal/* — для бота (по INTERNAL_API_TOKEN),
             /api/* — для админки (вход по логину и паролю, cookie)
  bot/       MAX: принимает сообщения и отвечает. Данные берет из API, контент держит в кеше
  admin/     React + Vite + Ant Design: редактор дерева, служебные тексты и история версий, сотрудники и журнал действий
packages/
  core/      контент (дерево, начальный контент seed-data.ts) и диалоговый движок; без БД и сети
  db/        схема Drizzle, миграции (drizzle/), заливка начального контента
  runtime/   общий .env, логгер (logs/<приложение>.log)
tools/
  image-generator/   картинки расписаний и тарифов в media/generated
```

Если API недоступен, бот продолжает отвечать по последнему загруженному контенту, а сессии держит в памяти.
Одновременно работает только один бот: он держит аренду в API, второй экземпляр завершается.

## Быстрый старт (локально)

Нужны Node.js 20.19+, pnpm и Docker.

```bash
pnpm install
cp .env.example .env          # вписать BOT_TOKEN и INTERNAL_API_TOKEN (любая длинная случайная строка)
docker compose up -d          # PostgreSQL на localhost:5433
pnpm admin:create admin       # первый суперадмин (пароль спросит в консоли), остальных он добавит из админки
pnpm dev                      # API :3001, бот (polling) и админка http://localhost:5173
```

При запуске API сам применяет миграции и, если БД пустая, заливает начальный контент из
`packages/core/src/content/seed-data.ts`. Уже заполненную БД он не трогает: правки из админки сохраняются.
Приложения можно запускать и по отдельности: `pnpm dev:api`, `pnpm dev:bot`, `pnpm dev:admin`.

### Без токена: симулятор чата

```bash
pnpm chat                                    # интерактивно
pnpm chat "как купить билет" "якутск"        # прогнать реплики
pnpm chat --api                              # контент из запущенного API, а не из seed-data.ts
```

- текст — сообщение пользователя;
- `?фраза` — показать косинусное сходство E5 с разделами (без генерации ответа).

## Как бот понимает текст

1. Приветствие («Здравствуйте, …») отрезается; на чистое приветствие бот отвечает стартовым сообщением.
2. «назад», «меню», номера пунктов и «да/нет» — детерминированная навигация.
3. Если ответ состоит из слов названия показанного варианта («Якутск» при кнопке «Якутск — Нижний Бестях»),
   выбирается этот вариант; при 2–3 совпадениях бот переспрашивает. В корневом меню не применяется.
4. Иначе — смысловой поиск по всему контенту в два шага, локально на CPU, без внешнего API:
   - **E5** (`Xenova/multilingual-e5-small`, q8, закреплённая ревизия) кодирует вопрос (`query:`) и фрагменты
     контента (`passage:`) и отбирает 10 лучших разделов по косинусному сходству;
   - **реранкер** `onnx-community/bge-reranker-v2-m3-ONNX` (q8) читает пары «вопрос — лучший фрагмент раздела»
     и пересчитывает оценку; к его логиту добавляется отставание E5 от лидера (`RERANK_E5_WEIGHT`), итог — сигмоида.
5. В индекс входят путь раздела, абзацы и пункты ответа (отдельно, чтобы факты не сливались), название раздела
   как вопрос (`query: <название>`), текст с картинки (`content_nodes.image_text`, каждая строка — отдельный факт)
   и синонимы раздела (`content_nodes.synonyms`) — метаданные «как об этом спрашивают». Синонимы кодируются моделью
   так же, как название: помогают похожим формулировкам, но слово из синонима в постороннем вопросе ответ не включает.
   Лучше писать их фразами и вопросами; одиночные названия станций у касс уводили в кассу вопросы о маршрутах.
   Правил «слово → раздел» и стеммера в коде нет: после правки контента индекс строится заново.
   Глобальный поиск получает только сам вопрос, без прошлой темы.
6. Решение по оценкам (пороги — в `semantic-config.ts`):
   - лидер ≥ 0,9 и отрыв от второго ≥ 0,15 — сразу ответ;
   - иначе, если есть кандидаты ≥ 0,02, — «Уточните, пожалуйста, что Вас интересует:» с 1–3 вариантами
     (неуверенный лидер никогда не отвечается напрямую); последний пункт — «Нет подходящего варианта — служба
     поддержки» (настройки `text.handoff` и `search.handoff`, код раздела; пустой код убирает пункт);
   - иначе — подсказка со списком тем и запись в `unrecognized_messages`.
7. Поиск не сочиняет ответы: возвращаются исходные тексты/картинки/файлы выбранного раздела.
   При ошибке модели бот предлагает повторить вопрос или выбрать пункт номером.

### Качество и как его мерить

Вопросы реальных пассажиров (MAX — `dialog_events`, Telegram-бот — `metric_messages`) с размеченными
правильными разделами лежат в `apps/bot/src/evaluation/real-*.ts`; `fixtures.ts` — 71 старая контрольная реплика.

```bash
pnpm retrieval:report [--rerank=0]   # hit@1/3/5 и MRR поиска без диалоговой логики
pnpm eval:e5 [--real] [--strict]     # прогон диалогов → .cache/e5-evaluation.json / e5-real.json
pnpm calibrate:policy                # подбор порогов на 60% реальных диалогов, проверка на остальных 40%
```

Поиск (146 уникальных реальных вопросов): правильный раздел первым — 96 (66%), в тройке — 126 (86%),
в пятёрке — 131 (90%). Только E5 без реранкера давал 71 / 91, без синонимов — 91 / 115.

Диалоги на реальных вопросах. «Полезно» — верный ответ сразу или в вариантах уточнения, а для вопросов,
ответа на которые в контенте нет, — путь в поддержку. Отложенная часть (90 реплик) при подборе порогов не использовалась.

| | Сразу верно | Полезно | Неверных прямых ответов |
|---|---|---|---|
| Отложенная часть: прежний поиск по ключевым словам и синонимам (`main`) | 63% | 78% | 11 |
| Отложенная часть: E5 + реранкер + синонимы + пункт «в поддержку» | 58% | 89% | 2 |
| Все 226 реплик: прежний поиск | 67% | 79% | 24 |
| Все 226 реплик: E5 + реранкер + синонимы + пункт «в поддержку» | 54% | 85% | 4 |

Оставшиеся промахи: реплики, понятные только из контекста переписки («1», «И 1. И 2.»), пары станций без слов
«цена»/«расписание», опечатки в названиях. Посторонние фразы обычно получают уточнение с пунктом «в поддержку»
вместо отказа; `RERANK_CLARIFY_THRESHOLD=0.2` делает уточнения реже (отложенная часть: 80% полезных вместо 89%).
Часть синонимов писалась, когда эти вопросы уже приходили, поэтому цифры могут быть немного завышены.

Первый запуск скачивает модели (~700 МБ) в `.cache/e5` (`E5_CACHE_DIR`). Память — ~1,7 ГБ, ответ — ~0,35 с
на 2 vCPU. `RERANK_DEPTH=0` оставляет только E5 (~0,5 ГБ, пороги `E5_THRESHOLD`/`E5_AMBIGUITY_GAP`).

## Типы разделов (`content_nodes.type`)

| Тип       | Что делает |
|-----------|------------|
| `section` | Сообщение (текст, картинка, файл). Вложенные пункты перечисляются в сообщении как варианты ответа (уточняющий вопрос); без них — конечный ответ |
| `link`    | Ссылка на внешний сайт (в списке вариантов — кликабельная) |
| `goto`    | Вариант ответа, ведущий в другой раздел (без дублирования текста) |

`is_hidden` — раздел не перечисляется в вариантах, но находится по тексту (так сделан «Возврат билета»).
`is_active` — выключенный раздел и все вложенные в него не перечисляются и не находятся.

## Роли сотрудников

| Роль | Что доступно |
|------|--------------|
| Суперадмин | Всё, в том числе управление админами и журнал действий |
| Админ | Контент и управление сотрудниками поддержки |
| Поддержка | Только чат (появится позже) |

Сотрудника добавляют на экране «Сотрудники»: система выдает одноразовую ссылку на 48 часов, по ней он сам задает пароль.
Этой же ссылкой сбрасывается забытый пароль. Сотрудников не удаляют, а отключают: доступ закрывается сразу на всех
устройствах. Нельзя отключить или понизить самого себя и последнего суперадмина.

## Настройки: служебные тексты и история версий

Экран «Настройки» доступен суперадмину и админу. Служебные тексты правятся обычной формой; если текст успел изменить
другой сотрудник, правка не применится и форма предложит обновить страницу.

Каждая правка контента или текстов сохраняет снимок всего контента в `content_versions` и запись в журнале с хешем версии.
Кнопка «Вернуть» приводит разделы и тексты к выбранному снимку: разделы сохраняют свои id, текущая версия остается в истории.
Если в версии другие картинки или текст с картинки, вернуть ее может только суперадмин. В снимках нет истории файлов:
при загрузке файлов (следующий этап) их нельзя будет удалять, пока на них ссылается снимок.

Снимки не удаляются, таблица растет примерно на размер контента за правку.

| Команда | Что делает |

| `pnpm db:generate` | Миграция после изменения `packages/db/src/schema.ts` |
| `pnpm db:migrate`, `pnpm db:seed [--force]` | Миграции и начальный контент вручную (`--force` заменяет контент в БД на seed-data.ts и стирает правки из админки; при `NODE_ENV=production` запрещён) |

## Сертификаты

API MAX подписан сертификатом НУЦ Минцифры (Russian Trusted Root CA), которого нет в Node.js.
Сертификаты лежат в `apps/bot/certs/` и подключаются только для процесса бота (`apps/bot/src/tls.ts`).
На Node.js < 22.19 запускайте бота с `NODE_EXTRA_CA_CERTS=<абсолютный путь к apps/bot/certs/russian_trusted_root_ca.pem>`.
