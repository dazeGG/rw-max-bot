# Развертывание

Сервер: `87.242.88.90` (Ubuntu 24.04), домен `max-bot.rw-y.ru`. Все работает в Docker:

| Сервис     | Что делает | Наружу |
|------------|------------|--------|
| `web`      | Caddy: HTTPS (сертификат Let's Encrypt выпускается и продлевается сам), прокси `/webhook` → бот | 80, 443 |
| `api`      | API, единственный работает с БД; при старте применяет миграции и заливает контент в пустую БД | — |
| `bot`      | Бот в режиме webhook | — |
| `postgres` | PostgreSQL 16, данные в томе `rw-max-bot_pgdata` | — |

Загруженные картинки и файлы разделов лежат в томе `rw-max-bot_uploads`: API в него пишет, бот читает.

`/internal/*` (запросы бота к API) снаружи недоступен: бот ходит в API внутри docker-сети.

## Админка

На этот сервер админка не выкладывается: ее нет в образах, а снаружи на `max-bot.rw-y.ru` отвечает только `/webhook`,
остальное — 404. API работает внутри docker-сети для бота. Выкладка админки в закрытый контур компании будет отдельной.

Для разработки админка работает на [дев-стенде](dev/README.md).

## Первый запуск

```bash
# 1. Docker, ufw (80, 443) и /opt/rw-max-bot/.env с секретами
ssh root@87.242.88.90 'bash -s' < deploy/server-setup.sh

# 2. Вписать токен бота
ssh root@87.242.88.90 'nano /opt/rw-max-bot/.env'      # BOT_TOKEN=...

# 3. Выложить текущий коммит
deploy/deploy.sh
```

**Важно:** для разработки есть отдельный тестовый бот со своим токеном, он работает на [дев-стенде](dev/README.md).
Подписка на вебхук у бота одна, поэтому один токен нельзя использовать на двух серверах.

## Обновление

```bash
deploy/deploy.sh      # выкладывает HEAD; незакоммиченные правки не попадают на сервер
```

Код лежит в `/opt/rw-max-bot/src` и заменяется целиком, `.env` — в `/opt/rw-max-bot/.env` и не трогается.
Выложенный коммит — в `/opt/rw-max-bot/src/REVISION`.

### Первая выкладка ролей сотрудников

Миграция `0005_staff_roles` применяется при старте API: прежний `admin` становится суперадмином, прежний `editor` —
админом, ФИО заполняется логином (его можно исправить на экране «Сотрудники»). Пароли и входы остаются. Ручных шагов нет.

### Запуск чата поддержки

Чат выключен настройкой `SUPPORT_CHAT_ENABLED=false`: бот не показывает пункты «Написать оператору», не создает обращений и не передает сообщения сотрудникам.
Миграция `0007_support_chat` к тому же добавляет эти пункты на рабочую базу выключенными. Раздел «Служба поддержки» с телефонами работает как обычно.
Включайте чат только когда сотрудникам открыта админка, иначе пассажиры будут писать в пустоту, а бот не будет им отвечать.

1. Заполнить на экране «Настройки» часы работы поддержки.
2. На экране «Контент» включить раздел «Написать оператору» в «Службе поддержки» и пункт с таким же названием в главном меню.
3. Проверить синонимы раздела «Написать оператору» (позвать оператора, поговорить с человеком, живой человек, нужен оператор…) и убрать «оператор» и «живой человек» у «Службы поддержки»: на рабочей базе они остались там, и оператор конкурировал бы с телефонами. При включенном чате поиск открывает обращение сам, когда уверен, что пассажир просит человека.
4. Указать `SUPPORT_CHAT_ENABLED=true` в `/opt/rw-max-bot/.env` и пересоздать бота: `deploy/deploy.sh`.

Файлы чата — личные данные пассажиров. Они лежат в том же томе `rw-max-bot_uploads`, в папке `support`, и попадают
в его резервную копию (см. «Обслуживание»).

### Первая выкладка смыслового поиска (E5 + реранкер)

- При первом старте бот скачивает модели (~700 МБ) в том `rw-max-bot_models`; это несколько минут,
  затем — ~15 с на загрузку. Нужен доступ сервера к huggingface.co.
- Бот занимает ~1,7 ГБ памяти (`mem_limit: 2500m`), ответ на свободный вопрос — ~0,35 с (до ~1 с).
- Миграция `0004_image_text` добавит пустую колонку `content_nodes.image_text`: API применяет миграции
  при старте, но существующий контент не перезаписывает. Текст с картинки тарифов нужно внести вручную,
  иначе вопросы о ценах до станций не находят ответ (из `/opt/rw-max-bot/src/deploy`):

```bash
docker compose --env-file /opt/rw-max-bot/.env exec -T postgres psql -U rw rw_max_bot <<'SQL'
UPDATE content_nodes SET image_text = $t$На проезд в поездах №317, №327 / №318, №328. Цена билета со станции Нижний Бестях: плацкарт, купе

Томмот: плацкарт 2 039 ₽, купе от 2 803 ₽
Алдан: плацкарт 2 261 ₽, купе от 3 145 ₽
Нерюнгри: плацкарт 2 759 ₽, купе от 3 912 ₽
Тында: плацкарт 3 427 ₽, купе от 4 938 ₽
Белогорск: плацкарт 4 981 ₽, купе от 7 326 ₽
Благовещенск: плацкарт 5 425 ₽, купе от 8 797 ₽
Хабаровск: плацкарт 6 996 ₽, купе от 10 390 ₽
Уссурийск: плацкарт 8 941 ₽, купе от 13 367 ₽
Владивосток: плацкарт 8 941 ₽, купе от 13 367 ₽
Чита: плацкарт 6 996 ₽
Улан-Удэ: плацкарт 8 454 ₽
Иркутск: плацкарт 9 426 ₽$t$
WHERE code = 'tariffs-yakutia';
SQL
```

  Потом этот текст меняет суперадмин в админке (раздел → «Текст с картинки»).
  В SQL — цены из `seed-data.ts`, сверьте с картинкой.
- Синонимы разделов (`content_nodes.synonyms`) теперь участвуют в смысловом поиске как метаданные.
  Однословные названия станций у касс уводят вопросы о маршрутах («Якутск Владивосток») в кассу — их нужно убрать:

```bash
docker compose --env-file /opt/rw-max-bot/.env exec -T postgres psql -U rw rw_max_bot <<'SQL'
UPDATE content_nodes
SET synonyms = ARRAY(SELECT s FROM unnest(synonyms) AS s WHERE s NOT IN ('томмот', 'алдан', 'нижний бестях', 'бестях', 'якутск'))
WHERE code IN ('buy-tommot', 'buy-aldan', 'buy-bestyakh', 'buy-yakutsk');
SQL
```

- После обоих SQL — обновление контента (см. ниже): бот перестроит индекс.
- В каждом уточнении поиска последний пункт — «Нет подходящего варианта — служба поддержки». Текст и раздел
  задаются настройками `text.handoff` и `search.handoff` (код раздела, по умолчанию `support`; пустое значение
  убирает пункт). Когда чат поддержки включен, последний пункт называется по `text.handoffOperator` и ведет сразу
  к оператору, см. «Запуск чата поддержки».
- Пороги откалиброваны (`pnpm calibrate:policy`) и в `.env` не нужны; переопределения — в `.env.example`.
  `RERANK_DEPTH=0` возвращает поиск только на E5 (~0,5 ГБ памяти, качество ниже).

## Обслуживание

### Немедленное обновление контента после SQL-правок

Правки из админки применяются сами. После SQL вызовите внутренний метод API.
На сервере из `/opt/rw-max-bot/src/deploy`:

```bash
docker compose --env-file /opt/rw-max-bot/.env exec -T api node --input-type=module <<'JS'
const response = await fetch('http://127.0.0.1:3001/internal/content/refresh', {
  method: 'POST',
  headers: { authorization: `Bearer ${process.env.INTERNAL_API_TOKEN}` },
});
console.log(response.status, await response.text());
if (!response.ok) process.exitCode = 1;
JS
```

API отправляет `POST http://bot:3002/internal/content/refresh`. Бот загружает контент через API,
затем возвращает `{ "ok": true, "version": "..." }`. Порт 3002 не опубликован наружу, оба метода
защищены `INTERNAL_API_TOKEN`; наружу Caddy отдает только вебхук. При ошибке возвращается 503:
данные в БД не откатываются, бот сохраняет прежний кеш; можно повторить запрос или дождаться резервной проверки.

Резервный опрос — раз в 5 минут (`CONTENT_REFRESH_SECONDS=300`). При обновлении существующей установки
замените старое значение `CONTENT_REFRESH_SECONDS=30` в `/opt/rw-max-bot/.env` на `300` и пересоздайте
контейнер бота через `docker compose --env-file /opt/rw-max-bot/.env up -d bot`. Обычный `restart`
не применяет изменения переменных окружения. Для новой функциональности сначала нужна выкладка кода.

```bash
ssh root@87.242.88.90
cd /opt/rw-max-bot/src/deploy
alias dc='docker compose --env-file /opt/rw-max-bot/.env'

dc ps                       # состояние
dc logs -f bot              # журнал бота (api, web, postgres — так же)
dc restart bot
dc exec -T postgres pg_dump -U rw rw_max_bot > /root/backup-$(date +%F).sql     # резервная копия БД
docker run --rm -v rw-max-bot_uploads:/data:ro -v /root:/backup alpine tar czf /backup/uploads-$(date +%F).tar.gz -C /data .     # загруженные файлы
```

Журналы приложений также пишутся в том `rw-max-bot_logs` (`api.log`, `bot.log`, `*-error.log`).
